# Smackend architecture proposal

Design review, 25 November 2026. All interfaces below are proposals. Latency budgets, supported deployment profiles and installation times are acceptance targets awaiting measurement.

## 1. What is worth building?

TypeQuest worked with vanilla pages, Flask and SQLite. The problem to solve is what happens to a working login when the next hackathon requirement lands. Choose a backend by the number of security and data contracts a feature author must maintain. Raw request throughput is a secondary criterion until measurements identify a bottleneck.

Build **a small installable Django toolkit, a reference deployment and a regression suite that runs against the consuming app**. Use one Python service and one PostgreSQL database. A developer adds an ordinary Django app for each substantial business capability. Keep stable authentication code in a versioned dependency. A stock Django project with documented settings is the baseline competitor. If Smackend cannot measurably improve setup time or catch regressions beyond that baseline, ship the recipes and tests alone.

Use synchronous database services first, Uvicorn as the ASGI server, Docker Compose for reproducible development, pytest/pytest-django for behavior, HTTPX for outbound calls and live HTTP tests, and Locust for scheduled load exercises. Keep test tools out of runtime dependencies. ## 2. Runtime and ownership

The browser loads static HTML, CSS and JavaScript and calls the same HTTPS origin under an API prefix. A reverse proxy can route static and API requests to different processes behind that origin. Django resolves a session, DRF validates the request, the feature obtains an authorized queryset, and its service executes the business transaction. The serializer explicitly selects fields for the response. The frontend owns all navigation and rendering.

| Boundary | Depends on | Owns and exposes |
|---|---|---|
| Core | Django, PostgreSQL settings | Validated profiles, diagnostic checks, API error handling, request IDs and health views. Can boot a public app with identity disabled. |
| Browser identity | Core, Django auth/sessions, allauth | One configuration profile mapping to upstream settings and URLs, plus tested session, signup and logout contracts. Domain tables refer to the host's user model. |
| Access control | Authenticated principal when required | DRF defaults and reusable policy examples. The host app defines the meaning of ownership, team membership, delegation and state-dependent permissions. |
| Consumer features | Core and explicitly enabled capabilities | Models, migrations, urls, serializers, policies, service functions and tests. Two features integrate by calling a documented service or referencing a declared model. |
| Optional integrations | Consumer-owned initially | File storage and HTTP clients live beside their first caller. Extract shared behavior only after another consumer needs it. |
| Verification | Installed package plus consumer config | Checks the final URL configuration, enabled profiles, schema, permission rules and real endpoints. Never import test fixtures into runtime. |

**Lifecycle.** The host settings and URLconf are the composition root. A proposed settings helper expands an explicit profile into installed apps, middleware order and required settings. Register Django system checks for missing dependencies, conflicting settings, repeated routes, unsafe cookie flags and unavailable migration prerequisites. Validate the declared module graph before serving traffic and report the dependency path for a missing node or cycle. Use fixed, documented dependencies for built-ins. Third-party apps use normal Django registration. Avoid package scanning, dynamic installation, custom DI and a second plugin lifecycle.

Use app initialization for registering checks only. Avoid network access and migrations during imports or AppConfig.ready(). A release job runs migrations once. Provision process-scoped resources through an explicit host lifecycle owner if needed, create them after worker fork, close them on shutdown, and bound graceful drain time. The first outbound adapter may use a context-managed client per operation if reuse has not justified lifecycle complexity. Business services take dependencies as arguments, e.g. a delivery service accepts a mail sender and a clock. A failing optional provider affects its caller only. Python modules in one process share memory and CPU; a module boundary cannot contain a process crash.

**Public contract.** Version the profile keys, URL names, JSON schemas, error codes, diagnostic exit status, and consumer verification fixtures. Document each supported hook with an example, lifecycle, inputs, outputs and failure semantics. Keep Django request objects, querysets, routers, transactions and ASGI callable accessible. Never require a generic repository, universal CRUD base class or framework-neutral model language. Disable a shipped module by withdrawing its routes after first checking dependents. Retain its migration history and data. Deletion is a separate planned migration.

### Proposed tree and consumer workflow

```text
Smackend/
  pyproject.toml                 # package metadata, extras and tested dependency bounds
  src/smackend/{core,identity,access,verification}/
  infra/                         # database image configuration, Compose and release runbook
  examples/expenses/             # separate consuming project, with its own Django settings
    config/                      # settings, urls, ASGI
    expenses/                    # models, policies, services, views, migrations, tests
    frontend/expenses/           # expenses.html, expenses.css, expenses.js
  tests/{contracts,integration,upgrade,load}/
  docs/{architecture,modules,api,operations}/
  AGENTS.md
```

An event team installs a tagged wheel from an index or a vetted build, pins it in its own lock file, starts PostgreSQL, registers its own Django apps, runs migrations, then starts the server. The package and database infrastructure definitions live in this repository. Database contents, uploads and credentials live outside Git. Support one Python minor and PostgreSQL major initially; candidate baseline Python 3.12 and PostgreSQL 17. Prove the dependency set on Linux CI and a Windows-hosted Compose quickstart before advertising support. Publish a wheel and sdist only after installing each in a clean environment and checking migration files and optional extras. [Python packaging guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)

**Three interaction levels, illustrated with an expense app** (conceptual pseudocode).

```text
Configure: enable browser_identity(username, password); mount its browser URLs.
Extend:    install expenses; include expenses.urls under /api/v1/expenses/.
           Expense has owner → settings.AUTH_USER_MODEL, amount, currency, created_at.
           list_expenses(request) starts with Expense.objects.filter(owner=request.user).
           create_expense(actor, validated_input) derives owner from actor.
Control:   implement monthly_totals(actor) with an ORM aggregate or parameterized SQL.
           Register an ordinary DRF view for the result and a separate URL for CSV export.
```

A static login page gets a CSRF cookie using a same-origin bootstrap endpoint, posts the documented allauth browser payload with the CSRF header, then reads current session state. After login it reads the fresh CSRF token before the next write. Each page can use a tiny fetch helper while retaining its own same-named HTML, CSS and JS files. Test a full navigation, refresh, expired session and logout in a real browser. Keep allauth's published browser protocol intact and document its validation and session-state responses alongside the domain API. [Allauth API specification](https://docs.allauth.org/en/latest/headless/openapi-specification/) · [Django CSRF](https://docs.djangoproject.com/en/stable/ref/csrf/)

## 3. Scope and identity design

| Ship in 0.1 | Next, when validated | Defer until a consumer pays the complexity cost |
|---|---|---|
| Core, PostgreSQL migration workflow, browser password sessions, username signup, session introspection, logout, role and ownership example, read/write API contracts, packaged verification | Verified email and recovery with a delivery provider, safe staff administration, private asset recipe, outbound HTTP recipe | Social linking, phone/SMS OTP, mobile tokens, general admin UI, hosted file integrations, workers, model routing, voice, WebSockets and multi-tenant isolation profiles |

**Separate what a user supplies from what proves identity.** Registration fields describe input (e.g. required username and password, optional display name). A login identifier locates an account. An authentication method proves control of a credential. Verification proves control of an address or number. Keep profile fields in an app-owned one-to-one model; changing a display name cannot change who can log in. Expose a small set of tested combinations. Reject an enabled login identifier without a supported enrollment path, email recovery without verified addresses, or a delivery flow without a provider. [Allauth account configuration](https://docs.allauth.org/en/latest/account/configuration.html)

The host chooses its user model before the first migration; use a minimal host-owned AbstractUser subclass in the reference app. Reusable apps reference settings.AUTH_USER_MODEL. Use an immutable internal ID for relationships. In the first profile restrict usernames to a documented ASCII alphabet and store a single canonical lowercase representation. Enforce canonical uniqueness in PostgreSQL across all entry points, including admin and imports. Reject a second concurrent insert through the constraint and translate that particular conflict only. Display names can support Unicode independently. When email login ships, document the normalization policy, reserve identity changes until verified, and rehearse conversion of existing records before turning on uniqueness. [Django user model guidance](https://docs.djangoproject.com/en/stable/topics/auth/customizing/)

Reuse Django password validation and its Argon2 hasher with argon2-cffi. Exercise validators on every supported password-setting path. Benchmark CPU and peak memory per concurrent verification and cap in-flight hash work before deployment. Use a PostgreSQL-backed Django session and a host-only Secure, HttpOnly, SameSite=Lax session cookie on HTTPS. Enable CSRF on all browser state changes including anonymous login and logout. Keep GET side-effect free. Rotate the session identifier at login, expire on a documented absolute deadline (initial target 8 hours), flush on logout and test invalidation after password changes. Document how an operator disables an account; require subsequent requests to reject it. A stricter idle timeout or a per-device revocation console is a separate feature. Browser v0.1 needs no access/refresh-token pair. [Django password management](https://docs.djangoproject.com/en/stable/topics/auth/passwords/) · [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

**Rate limits are a release gate.** Allauth uses a Django cache and documents shared-state and eviction requirements. Process-local limits cannot protect a multi-worker deployment. Evaluate a dedicated PostgreSQL-backed Django cache for allauth's built-ins with bounded retention and verified capacity. For a strict admission cap across workers, evaluate a short atomic PostgreSQL counter update keyed by action, time bucket and keyed digest of identifier or trusted client address. Bound key creation and handle hot rows, window boundaries and pruning. Do not claim a hard guarantee from a cache read/modify/write. Reject excessive attempts with 429 and a retry hint; fail closed on unavailable protection for sensitive endpoints. Check every enabled login path including admin, size the budget with legitimate shared-network users, and trust proxy headers only from the configured proxy. The exact backend is open pending the synchronized test below. [Allauth deployment requirements](https://docs.allauth.org/en/latest/common/rate_limits.html)

**Recovery and federation.** Username-only demos need an explicit notice that self-service recovery is unavailable. For a public-facing release require a tested verified-email recovery profile or an approved operational recovery process. Use allauth reset flows, generic responses, expiring single-use credentials and verified sender configuration. Test delivery failures, repeat requests, replay and session invalidation. Phone OTP additionally needs a sender, cost cap, attempt limit, resend policy and protection against number reassignment. For future social login use upstream OAuth/OIDC adapters, validate callback/state and provider identity, and key links by issuer and subject. Require proof of control of the existing account before linking. Evaluate mobile tokens separately, including storage, audience, rotation, refresh reuse and immediate revocation requirements.

**Authorization.** Require authentication by default on domain APIs. Each action also needs its own permission decision; explicitly list public routes. Use Django groups for coarse roles and feature-owned policy functions for row scope and allowed transitions. Scope list, detail, count, search, export and aggregate queries before pagination. For creates, resolve the permitted parent and derive ownership on the server. For updates verify both current scope and the proposed new relationship. A support role may view an order yet lack permission to refund it. Keep staff access separate from domain privileges. Expose admin only on an explicitly protected deployment profile, with narrow model registrations, row filters, field restrictions, audit events and stronger staff authentication before use on the public internet. [DRF permission limits](https://www.django-rest-framework.org/api-guide/permissions/) · [DRF authentication](https://www.django-rest-framework.org/api-guide/authentication/)

## 4. PostgreSQL, operations and failure behavior

Use foreign keys, uniqueness and check constraints for invariants. Pick deletion behavior per relationship. Index actual access paths, such as (owner_id, created_at, id) for a stable time-ordered feed. Allowlist filter and sort fields, bound page sizes, and add keyset pagination when many inserts or deep pages make offsets unsuitable. Start search with indexed exact/prefix fields as appropriate; justify full text with an actual query and plan. Keep SQL parameters separate from values, allowlist dynamic identifiers, and use explicit response fields. Inspect plans on representative data and test for N+1 queries.

One application command owns one short atomic transaction. For stock reservation, conditionally decrement where remaining stock is sufficient, check the affected-row count and insert the order in the same transaction. Use uniqueness on a scoped idempotency key for retryable commands and verify the payload matches on replay. Use row locks where a decision spans existing rows, acquire in stable order, and bound waits. Retry a whole transaction only for classified transient conflicts and within a deadline. Keep external calls outside locks; use a transactional outbox when external delivery becomes durable business state. A connection loss during commit can leave the outcome unknown. Reconcile by operation ID before reporting or retrying. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html) · [Django transactions](https://docs.djangoproject.com/en/stable/topics/db/transactions/)

Use psycopg pooling integrated with the Django backend. Under ASGI disable Django persistent connections. Budget pool maximum × processes × replicas plus release, diagnostics and admin headroom below PostgreSQL's usable connection limit. Set finite acquisition, statement and lock timeouts. Recycle broken connections at request boundaries. Never reuse a failed transaction. Consider PostgreSQL row-level security for a future multi-tenant profile once roles, pool reset semantics and privileged maintenance have independent tests. [Django database connections](https://docs.djangoproject.com/en/5.2/ref/databases/) · [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

**Schema evolution.** Each app owns its migrations and cross-app dependencies. Review generated SQL, lock levels, defaults, indexes, runtime and reversibility. CI migrates both an empty database and a seeded database from the previous supported release. For a rename or required field, add a compatible nullable column, deploy compatible writers, backfill in resumable batches, validate constraints, switch reads, then remove the old field in a later release. Serialize releases. Use a migration role with DDL privileges and a restricted runtime role. Back up before risky changes; rehearse restoration into a separate database and compare record counts and invariants. Roll back the app only while the previous binary remains compatible with the schema; otherwise forward-fix or invoke a rehearsed restore with explicit data-loss bounds. [Django migrations](https://docs.djangoproject.com/en/stable/topics/migrations/)

| Condition or threat | Behavior the operator or caller should see |
|---|---|
| Invalid settings, missing dependency, stale schema | Nonzero diagnostic with key and remedy, secret values redacted. Block release/readiness. |
| Invalid input or constraint conflict | Domain APIs return 400 for validation and 409 for a named business conflict, with stable code and field details. Preserve upstream identity response contracts. |
| Missing authentication, forbidden action, hidden object | Document the actual auth backend's unauthenticated status (DRF session auth can return 403). Stable application error codes distinguish login-required and forbidden. Return 404 for an out-of-scope private object where existence must remain private. |
| Cross-origin request, stolen credential, excessive attempts | Restrict trusted hosts and origins, enforce HTTPS and CSRF, escape untrusted frontend content, keep credentials out of browser storage and logs. Record outcome and request ID. SameSite and CORS alone cannot secure authenticated writes. |
| DB unavailable or saturated | Bounded 503 on dependent routes, liveness stays up, readiness fails. Probe recovery using a bounded DB check. Return success for a write only after its transaction commits. |
| Slow or malformed external API | Per-provider connect/read/write/pool timeouts plus a total deadline, response-size/schema limits and bounded concurrency. Honor Retry-After within deadline. Retry only safe/idempotent operations with bounded backoff and jitter. Surface 502/504 or an explicit partial result. [HTTPX timeouts](https://www.python-httpx.org/advanced/timeouts/) |
| Untrusted URL or upload | Prefer fixed provider origins, restrict redirects and egress. For future assets use server-generated keys, size/type/content limits, private storage, owner checks on download, and quarantine pending validation. Record pending/ready/failed states, clean orphan blobs and distinguish unauthorized/missing assets from storage outages. |
| Unexpected exception or resource exhaustion | Sanitized 500 with request ID, structured internal exception record, bounded queues/body sizes and process limits. Monitor error codes, latency, pool waits, DB locks, hash concurrency and dependency failures. Redact cookies, tokens, passwords, private document contents and provider payloads. |

Production uses a TLS proxy, allowlisted hosts, environment-injected secrets, secure cookie defaults, explicit allowed origins and debug disabled. Parse settings once, validate types and flag unknown Smackend keys. Ship a development-only loopback profile. Keep database storage persistent and bind the dev database locally. Set a release job, backups and a restore owner. Health responses expose status only; private diagnostics show versions and failing dependencies. Schedule expired session/cache cleanup. A Compose quickstart on a laptop establishes reproducibility; production availability and backup retention depend on the operator.

## 5. Verification and performance contract

Run fast checks after each feature change: consumer settings checks, migration drift, endpoint inventory against the public-route allowlist, clean PostgreSQL migrations, identity lifecycle with CSRF enabled, permissions across two owners, and consumer feature tests. Run the checks on the **assembled consuming app**; testing the library alone misses middleware reordering and URL shadowing. Use ordinary pytest fixtures so the consumer can provide a user factory, URL configuration and representative protected resources. Run a browser smoke test on CI. Review auth/schema diffs as public API changes. Never let the verify command use a non-disposable database for destructive tests.

| Suite | Concrete oracle |
|---|---|
| Unit and configuration | Policy decision table covers actor, action, object and state. Reject login configuration with no enrollment path. Invalid optional feature configuration names the field. |
| Integration and browser | Actual PostgreSQL and live cookies. Register, log in, navigate to a second page, refresh, write with a rotated CSRF token, log out, confirm previous session is rejected. Reject invalid or missing CSRF. Assert secret-free errors. |
| Authorization contracts | Anonymous, owner A, owner B and limited staff exercise list, detail, mutation, reassignment, export and counts. Zero unauthorized rows, writes or leaked counts. Test both exposed and disabled modules. |
| Race tests | Use independent connections and a barrier with real commits (transactional pytest-django). Twenty simultaneous canonical-equivalent registrations yield exactly one account. One hundred reservations for ten items yield ten successes and zero negative stock. A retry with the same operation ID creates one effect. |
| Failure and recovery | In a disposable environment interrupt PostgreSQL during read, write and after commit. Reconcile ambiguous writes. Force provider timeout, invalid JSON and 429, then verify unrelated endpoints remain usable. Interrupt startup and drain in-flight requests at shutdown. |
| Upgrade and compatibility | Install previous wheel into a sample app, seed users and owned records, upgrade, migrate and verify login, row visibility and the extension's endpoints. Review API-schema diffs. Test a disabled module with retained data and a fresh install of the wheel without the source tree. |

**Proposed benchmark, not a measured capacity claim.** Pin versions, hash parameters, worker count, pool sizes, machine allocation and dataset in each report. Initial reference target: Linux with 4 vCPU/8 GiB shared between app and DB, two Uvicorn workers, pool max 8 each, PostgreSQL max connections 50, separate load generator, TLS proxy, 1,000 synthetic users and 100,000 owned rows. Record storage, CPU model, connection budget and warm/cold cache state. Use Locust for paced traffic and a coordinated barrier for bursts. A virtual user count alone does not specify requests per second.

1. Warm up two minutes. Hold 10, 20, 50 and 100 concurrent users for five minutes each with seeded 0.5–1.5 s think times. Mix 60% scoped reads, 20% writes, 15% aggregates and 5% session checks. Run password verification as a separate workload with distinct synthetic accounts. Record achieved throughput and per-route percentiles.
2. At 100 users target p95 reads ≤250 ms, writes ≤500 ms, aggregates ≤750 ms and unexpected errors <0.1% per class. At five admitted logins per second target p95 ≤1 s. Record expected policy denials and throttles separately. Zero lost writes, duplicate effects or cross-user disclosures at every level. Repeated trials must achieve the offered login rate and the stated traffic mix.
3. Burst 100 synchronized attempts across both workers. With a test quota of 10 per identifier per fixed window, at most 10 enter password verification for that key in the same window. Verify unrelated accounts still succeed within budget. Then run 200 users and increase until saturation; publish the first bottleneck and achieved rate. Under overload accept bounded rejection, zero data corruption, zero process kills and recovery to normal-load latency within 60 seconds of relief.
4. Soak 30 minutes at 100 users. Target combined app RSS <1.5 GiB, total DB connections <40, no pool starvation at nominal load and <10% app RSS growth between warmed 5-minute and final 5-minute medians. Restore DB availability after a 30-second outage; readiness and successful authenticated reads should return within 30 seconds. Investigate any miss before changing a target. Report measurements and distributions with the hardware record.

## 6. Incremental release plan

| Phase | Completion gate |
|---|---|
| 0. Validate the stack | In a later implementation spike, pin compatible dependencies and prove browser CSRF, session rotation, canonical uniqueness and cross-worker throttling on PostgreSQL. Compare time to complete the same login plus owned-record change with stock Django. Revisit the framework choice or narrow the supported profile if a gate fails. |
| 1. Package and boot | Clean wheel and sdist installs, disposable Compose database, migrations, readiness and actionable bad-config errors. A new developer reaches the first response in 15 minutes with Python and Docker preinstalled; record cold download time separately. |
| 2. Identity and access | Complete browser journey, concurrency and denial matrix pass in the expense app. Threat review includes every public route. Define and test logout, absolute expiry, account disablement and recovery limitations. |
| 3. Consumer verification | Add an unrelated feature using only consumer files. A deliberately broken session middleware order and a missing owner filter each cause a named check to fail. Restore them and pass the full suite. Target the default verification run under 3 minutes on reference CI. |
| 4. Release candidate | Rehearse old-to-new migration, wheel upgrade, app rollback and backup restoration. Pass reference load and failure tests, publish limits and document unresolved issues. Tag 0.1 only after review. |
| 5. Optional modules | Promote a recipe only when two distinct consumers need the same contract and failure semantics. Each module provides disable/reenable tests, docs, migration ownership and explicit operational dependencies. |

Prefer familiar commands. Initially use Django startproject/startapp, migrate and check. Prototype **doctor** for read-only config/schema/DB diagnostics and **verify** for disposable test execution. Introduce **new** only if timed setup remains slow; introduce **add** only for a repeatable operation that can preview changes and safely rerun. Publish a compatibility matrix for Python, PostgreSQL, Django and module versions. Lock the reference app and CI; declare tested dependency ranges in the library. During a hackathon pin the released toolkit. Ship fixes through a new version with upgrade notes. Before 1.0 flag every breaking change explicitly; once stable, deprecate before removal and reserve breaking contracts for major releases.

**Validation scenarios.** Use new disposable projects with the same released artifact. Keep the test clock, changed paths and verification result for each change.

| Consumer exercise | What would expose rigidity or a regression |
|---|---|
| Expenses → shared budgets | Add membership alongside private ownership. Totals, exports and pagination must honor the new scope while old private expenses stay private. |
| Shop → stock reservation and product images | Race to reserve the last item, repeat checkout after a timeout, deny an unauthorized image edit, simulate storage failure. |
| Clinic scheduling with synthetic records | Restrict assigned clinicians, revoke an assignment, separate receptionist fields and inspect access audit events. This exercise establishes specific access behavior; healthcare deployment requires its own privacy and operational review. |
| Document reader | Authorize access to a document and page, attach a provider adapter, then simulate a stream disconnect and provider outage. Future sockets must authorize both connection and document changes, handle cancellation/backpressure, and avoid holding DB transactions while streaming. |
| Ticketing and webhook ingestion | Redeem the last seat concurrently; accept duplicate, delayed and reordered provider events. A signed service-to-service callback needs a principal independent of browser users. |
| Ten-hour wildcard rehearsal | Start authenticated. Every 90 minutes add a table, a reviewer role, private uploads, a failed third-party call, then a streamed summary. Features may be app-specific or simulated. After each change run verification and repeat the existing browser session journey. Record time, failures caught and toolkit changes needed. Target zero edits to installed toolkit code. |

**Future design pressure.** Run document indexing, notifications and durable AI work from persisted jobs when restart recovery matters. First evaluate a PostgreSQL job table or maintained PostgreSQL-backed worker with idempotency, leases, retry caps and visibility. An in-process background task can be lost on restart. Choose a worker only after an actual durable workload exists. Model choice, JSON output validation, token/cost budgets and cancellation belong to the first AI consumer until a second use case establishes a reusable interface. Voice introduces latency, consent, session lifetime and bandwidth requirements that need their own load profile.

**Teaching and AI-assisted changes.** Each released module guide follows one real request from page to endpoint to database and back, naming actual files/functions, the policy decision, transaction owner, likely failures, diagnosis and tests that establish each guarantee. Keep an architecture decision log, public API examples, extension recipes, OpenAPI snapshots and a troubleshooting guide organized by symptom. The future consumer AGENTS.md should identify toolkit versus app-owned paths, describe how to add a route/model/migration, name the quick verification command, and require a policy test for each new protected action. A change is reviewable when the developer can explain who may perform it, what commits together, and how the app behaves when its dependency fails.

**Open decisions before claiming support.** Establish the exact dependency pins and shared throttling behavior in phase 0. Measure login hashing and pool limits on the target machine. Choose a mail provider and delivery guarantees only for the verified-email profile. Start with same-origin browser hosting; a separate frontend origin or native client needs a distinct tested credential contract. Keep tenant isolation, public staff administration and high-availability failover outside the first support promise. These boundaries let a team add domain features quickly while making the cost of a new security or deployment profile visible.
