# __PROJECT_NAME__

This project uses Django, Django Ninja and PostgreSQL. The files in `frontend/` are plain HTML, CSS and JavaScript. Django serves them from the same local origin as the API.

## Start

Smackend generated a private `.env` with local credentials. Verify that port 55432 is free. Change `POSTGRES_PORT` in `.env` if you already have a local database on that port.

The app pins the Smackend version that generated it. For an unpublished local build, point the first sync at the wheel directory with `uv sync --find-links /path/to/dist --python 3.11`.

```shell
uv sync --python 3.11
docker compose up -d --wait postgres
uv run python manage.py migrate
uv run smackend verify
uv run python manage.py runserver 127.0.0.1:8000
```

Open [the frontend](http://127.0.0.1:8000/) or [the Ninja API docs](http://127.0.0.1:8000/api/docs). The health endpoint at `/api/health` checks the application. `/api/ready` runs a trivial PostgreSQL query and returns 503 if the database cannot be used. Apply migrations before startup.

You can also run the same app through ASGI:

```shell
uv run uvicorn config.asgi:application --host 127.0.0.1 --port 8000 --lifespan off --no-proxy-headers --no-access-log
```

## Work on the application

- Put application models and views in normal Django apps created with `uv run python manage.py startapp <app_name>`. Register them in `config/settings.py` and use the standard `makemigrations`, `migrate`, and `test` commands.
- Use ordinary Django views in `config/urls.py` or add Ninja routers to `config/api.py`. The scaffold has public status endpoints. Add authentication and ownership checks before exposing private data.
- Edit `frontend/` directly. No JavaScript build step is required.
- Keep the generated `uv.lock` with your project so subsequent `uv sync --locked` installs reproduce the environment.

The named Compose volume persists through a normal `docker compose down`. The PostgreSQL password in your `.env` must match the password used to initialize that volume. Keep the real `.env` out of version control. If you start from a copy without it, use `.env.example` as a guide and generate fresh values for the two secrets before starting.

## Configuration

Django imports `config/settings.py` when a management command or ASGI server starts. `config/env.py` parses the optional UTF-8 `.env`, overlays the process environment, and validates the fields used to set Django's standard options. **Process environment wins over `.env`, which wins over defaults.** An explicitly blank value does not fall back to the lower priority setting. Malformed assignments identify a line number. Invalid values identify the setting and the expected format without echoing the supplied value. Restart the process after changing configuration.

| Setting | Development | Production |
|---|---|---|
| `DJANGO_ENV` | Defaults to `development`. | Set to `production`. |
| `DJANGO_SECRET_KEY` | Required. Generated by `smackend init`. | Use a deployment-specific random key of at least 50 characters. |
| `DJANGO_DEBUG` | Defaults to `false`. `true` or `1` can enable it on an isolated local server. | Must be `false` or `0`. |
| `DJANGO_ALLOWED_HOSTS` | Defaults to `127.0.0.1,localhost,[::1]`. | Required. Give exact host names or IPs without schemes, ports or wildcards. Loopback and unspecified IPs are rejected. |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Optional comma-separated HTTP or HTTPS origins. | Optional HTTPS origins. Set only for trusted origins that need to make unsafe requests. |
| `DJANGO_TRUST_PROXY_SSL_HEADER` | Defaults to `false`. | Opt in only under the proxy conditions below. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Required. The scaffold generates a password for the local database. | Required. Use a deployment-specific random password of at least 16 characters. |
| `POSTGRES_HOST`, `POSTGRES_PORT` | Default to `127.0.0.1` and `55432`. | Host is required. The port defaults to `5432`. |
| `POSTGRES_SSLMODE`, `POSTGRES_SSLROOTCERT` | SSL mode defaults to `prefer`. The CA path is optional. | Requires `verify-full`. Supply the CA path if your client does not already have the correct trust root. |

Use ASCII DNS names or punycode for hosts. In HTTP host lists and origins, put IPv6 literals in brackets. Use a bare IPv6 address for `POSTGRES_HOST`. An origin is a scheme, host and optional port, for example `https://app.example.com:8443`, without a trailing slash, credentials, query or fragment. For local Compose passwords containing dollar signs, single-quote the value in `.env` to keep Compose from interpolating it. Django reads values literally.

Production enables HTTPS redirects, secure session and CSRF cookies, HSTS for 300 seconds, and frame protection. Set up HTTPS before exposing the app. Keep proxy header trust off if there is no trusted ingress. If opting in, prevent clients from reaching the backend directly and configure the proxy to strip any incoming `X-Forwarded-Proto` before setting it to the actual client scheme. Configure any ASGI server proxy handling with the same trust boundary. The generated Compose service is for local development. Production PostgreSQL must present a trusted certificate for the configured host. Configuration validation checks the settings at startup. It does not test proxy deployment or certificate availability.

The existing Phase 1.1 `.env` format still works for development. To adopt Phase 1.2 in an existing generated app, add `config/env.py` and merge the config changes into your existing `config/settings.py`. Preserve your actual `.env` and app settings. Use `.env.example` to document new keys. The generator refuses to overwrite the project directory, including its credentials. Keep future module credentials optional while the corresponding module is disabled. Add the module's checks inside the relevant enabled branch of ordinary Django settings.

## PostgreSQL connections and timeouts

Smackend uses Django's native PostgreSQL backend with psycopg pooling. Django opens the pool on first database use. A request borrows on first SQL use, reuses that connection for its remaining SQL, and returns it at request cleanup. `CONN_MAX_AGE=0` prevents Django's persistent-connection mode from competing with the pool. Checkout health checks help discard broken connections after a restart. A cursor context closes the cursor. Closing the Django connection returns the underlying connection to the pool. [Django connection management](https://docs.djangoproject.com/en/5.2/ref/databases/) · [psycopg pooling](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)

| Environment variable | Default | What it limits |
|---|---:|---|
| `POSTGRES_POOL_MIN_SIZE` | 0 | Connections kept as the pool's minimum once opened. Range 0–128. |
| `POSTGRES_POOL_MAX_SIZE` | 4 | Connections per Django worker process and database alias. Range 1–128, at least the minimum. |
| `POSTGRES_CONNECT_TIMEOUT_SECONDS` | 3 | Opening a physical connection. Range 2–300 seconds. |
| `POSTGRES_POOL_TIMEOUT_SECONDS` | 4 | Waiting for a usable connection from the pool. Range 1–300 seconds. |
| `POSTGRES_STATEMENT_TIMEOUT_MS` | 3000 | Executing one PostgreSQL statement. |
| `POSTGRES_LOCK_TIMEOUT_MS` | 1000 | One PostgreSQL lock acquisition. |
| `POSTGRES_IDLE_IN_TRANSACTION_TIMEOUT_MS` | 10000 | A connected session idle inside an open transaction. PostgreSQL ends that session if the limit is exceeded. |

The three SQL settings accept 1–2,147,483,647 milliseconds. These are separate limits. Include the pool wait, SQL calls, and upstream HTTP in the overall request budget. Within a transaction, use `SET LOCAL` for temporary PostgreSQL options so they revert at the end of that transaction. A slower migration may need a command-specific override such as `POSTGRES_STATEMENT_TIMEOUT_MS=60000 uv run python manage.py migrate` in POSIX shells. Use an environment variable in the shell running the migration on Windows. [PostgreSQL timeout settings](https://www.postgresql.org/docs/17/runtime-config-client.html)

Budget connections across all replicas and workers using the same database, then allow for management commands, migrations, operators, other services, and rolling deployment overlap. For example, three replicas with two workers each and a pool maximum of four can open 24 connections for one alias. A fourth overlapping replica adds eight. Keep the total below the database's usable connection count after reserved slots. These defaults are starting limits for correctness. Tune them only after measuring the workload on the target deployment.

`/api/health` checks the app without connecting to PostgreSQL. `/api/ready` runs `SELECT 1` through the actual pool and returns 503 with `{"status":"unavailable"}` on failure. It can be temporarily unready after restart while usable connections are restored. Both routes discourage caching. Readiness tests connectivity and pool availability. Use normal migrations before serving traffic.

The installed Smackend error handlers give Ninja routes sanitized responses for expected database failures. Pool exhaustion and connectivity failures return 503, a canceled SQL statement returns 504, and lock conflicts, deadlocks or serialization failures return 409. Django views outside the API URL space use Django's normal error responses. An HTTP failure can occur after a database commit. The scaffold never replays writes. Use an idempotency key or reconcile the operation before retrying.

### Transactions and outbound calls

Use native `transaction.atomic()` around the SQL that must commit together. Allow exceptions to escape the block so Django rolls it back. Catch expected database exceptions outside the block. For a shared counter, use a database update with `F("value") + 1` rather than reading a value into Python and saving it later. Use a constraint or conditional update to enforce invariants. For a read-then-write decision that spans several statements, lock the selected rows inside the same block and keep it short. PostgreSQL's default isolation here is Read Committed. An uncommitted write is invisible to other connections. Separate reads may observe newer committed data. [Django transactions](https://docs.djangoproject.com/en/5.2/topics/db/transactions/)

Keep outbound HTTP outside database transactions. In a long async request, materialize its input in a single synchronous, thread-sensitive helper and return that connection before awaiting the upstream. Use this pattern only when the helper owns its work and no outer transaction is active. Import `sync_to_async` from `asgiref.sync` and `connection` from `django.db`.

```python
@sync_to_async(thread_sensitive=True)
def load_payload(caller_id, note_id):
    try:
        # Example using an application-owned model and an already scoped query.
        return notes_for_caller(caller_id).values("title").get(pk=note_id)
    finally:
        connection.close()


async def call_provider(caller_id, note_id):
    payload = await load_payload(caller_id, note_id)
    return await send_to_provider(payload)
```

Resolve any required database-backed identity and permissions inside that database step. Return plain data from it. Later database work can borrow again. Do not call `connection.close()` from the event loop to release a connection acquired in a thread, or while inside an open transaction. In a long-running synchronous task outside Django's request hooks, use `close_old_connections()` at the start and return the task's connection in a `finally` after its transaction has ended.

For older generated projects, merge the current configuration and API imports and install the pinned runtime dependencies. Existing PostgreSQL credentials and new defaults work together. Keep your own routes and migrations. If the database has already been migrated with Django's default user model, keep that model until you have designed a separate data migration.

## Application infrastructure

- `accounts.User` is the project-owned Django user model. Reference it using `settings.AUTH_USER_MODEL` in relationships. Put models and reviewed migrations in their owning Django apps.
- Register app-owned Ninja routers in `config/api.py`. Use native Ninja schemas, pagination and filters. Scope records before filtering, and give list queries a stable order.
- API failures include a public `code`, `message` and `request_id`. Logs go to stderr as JSON. Set `SMACKEND_LOG_LEVEL` in the environment or `.env` to adjust verbosity.
- Run `smackend verify` in the app's environment. It reports configuration, system, connectivity, migration and test status. Add ordinary Django tests to extend it. Run against an environment whose database role can create disposable databases. Verification never applies migrations to your application database.

## Optional browser accounts

Projects initialized with `smackend init <name> --auth` install the `auth` extra and start with username/password registration and login. Open `/account/` after applying migrations. Otherwise the module is off, and the project can start without allauth or any identity provider configuration.

Adjust the account settings shown in `.env.example` to collect email or phone numbers, require verification, enable codes or reset, or connect Google. The browser account and session protocol is available under `/identity/browser/v1/`, its OpenAPI document is under `/identity/openapi.json`, and project-owned profile examples are documented in `/api/docs`. See Smackend's Phase 2A guide for profile examples and provider setup.

Protect private Ninja routers with `smackend.identity.permissions.session_auth`. Scope every owner-sensitive query, including counts and exports. Add custom fields, groups and policy code in this project. Schedule `python manage.py clearauthlimits` and Django's `clearsessions` when deploying the module.

## Optional storage, admin and outbound HTTP

- Use `--storage` for managed file endpoints at `/api/files/`. Files default to private. Keep the local media directory persistent and outside publicly served directories. Schedule `python manage.py cleanupmedia`.
- Use `--admin` for native Django administration at `/admin/`. Sign in at `/account/` and confirm your identity before opening admin. Register application models with `admin_site` in `config/admin.py`.
- Use `--http` for outbound HTTP configuration. Define named trusted providers in `.env` and read credentials only for providers you configure. Use `smackend.outbound.client` from project code.

Storage and admin enable accounts during initialization. When enabling them later, also enable the account module and install its extra. Run `python manage.py check`, apply reviewed migrations, and run `smackend verify`. See the Smackend Phase 2 guide for operational details.

## Optional AI and real-time examples

Use `--ai` for authenticated AI examples and `--realtime` for Channels. Open `/assist/` after signing in. These flags enable browser accounts. AI also enables outbound HTTP. Both examples default to deterministic offline providers.

Use an ASGI server for streaming and WebSockets. Keep the browser origin in `SMACKEND_REALTIME_ORIGINS`. For example, run `uv run uvicorn config.asgi:application --host 127.0.0.1 --port 8000 --lifespan off --no-access-log --ws-max-size 4096 --ws-max-queue 8`. Microphone access requires a browser secure context. Configure real provider credentials in private environment variables only after reviewing the Phase 3 guide.
