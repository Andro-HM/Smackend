# Choosing Smackend’s HTTP and real-time foundation

Architecture decision proposal · 25 November 2026 · Companion to [the original blueprint](ARCHITECTURE.md)

## Recommendation

**Choose Django as the authority for browser identity, permissions, PostgreSQL models, migrations and admin. Prefer Django Ninja for typed application HTTP endpoints and optional Channels for WebSockets (option 2), subject to the feasibility gates below.** Use regular synchronous functions for transactional commands and async functions for waiting on multiple upstreams or clients. An application can use both without asking every feature author to choose a database stack. Keep Django/allauth’s headless account endpoints intact. The vanilla multi-page frontend can use one origin throughout.

The deciding workload is an authenticated user opening a document, asking a question, then talking to a voice provider while their document access can change. Ninja can handle the HTTP request inside Django. A Channels consumer can own the client socket and provider connection while using Django’s session machinery. The expensive design problem is deciding when that conversation must stop after logout, reassignment, or provider failure. Adding FastAPI does not solve that problem. Channels also requires an explicit origin policy, reauthorization and cancellation. [Django async support](https://docs.djangoproject.com/en/5.2/topics/async/) · [Ninja operation dispatch](https://github.com/vitalik/django-ninja/blob/master/ninja/operation.py) · [Channels authentication](https://channels.readthedocs.io/en/stable/topics/authentication.html)

**The hybrid is feasible. Reserve a mount point and keep business services callable from either transport. Promote FastAPI to a supported optional extra only if it wins the matched workload test or unlocks a concrete integration the Django path cannot support at comparable cost.** A ready-made FastAPI router from a critical vendor, for example, might justify the adapter even at equal throughput. An async provider SDK that simply exposes a Python coroutine can already be called from a Ninja async view or a Channels consumer. If dedicated CPU, independent releases or hard fault isolation become necessary, route the same public prefix to a separate process. That is a different deployment profile with different failure tests.

**Evidence status.** This is documentation research and a proposed experiment. No prototype, benchmark, compatibility test or security test was run. Capabilities below are attributed to upstream projects. Performance comparisons are hypotheses; all numeric gates are proposed product requirements. Django references target the 5.2 LTS baseline in the blueprint. Pin the exact compatible patch versions of every component for the trial and record them with the results.

### What each choice would own

1. **DRF.** Keep DRF session authentication and Django/allauth account routes. A consumer defines serializers, scopes its queryset, checks create permissions on the parent, and executes a service. A custom native Django async view is a legitimate escape hatch for HTTP streams; an async iterator is needed under ASGI. If the team prefers DRF’s serializer and viewset ecosystem and its mixed-load gate passes, retaining DRF with optional Channels is a useful fallback. Label that extra separately in socket comparisons. [Django streaming responses](https://docs.djangoproject.com/en/5.2/ref/request-response/#streaminghttpresponse-objects)
2. **Ninja/Channels.** Default protected Ninja routers to the supported session authenticator; require explicit review for public overrides. Use explicit input and output schemas to prevent assignment/disclosure of privileged fields. Keep Django views and middleware available. Let a consumer implement one socket handler for its protocol and reuse the same domain policies. Channels layers are optional for direct client-to-provider connections. A process-local group cannot deliver cross-worker broadcasts reliably. Shared room fan-out, durable notifications and seamless failover require another design and are outside this Redis-free profile. [Ninja authentication](https://django-ninja.dev/guide/authentication/) · [Channels layers](https://channels.readthedocs.io/en/stable/topics/channel_layers.html)
3. **Standalone FastAPI.** Test a concrete alternative: FastAPI, SQLAlchemy 2 async with psycopg, Alembic as sole schema owner, a maintained password hasher, server-side PostgreSQL sessions with opaque browser credentials, and explicit browser CSRF and staff controls. Evaluate FastAPI Users’ database token strategy and cookie transport as reuse candidates; verify logout, password-change invalidation, CSRF, recovery and admin before treating it as equivalent. Its maintainers describe maintenance mode. Once integrated, this option has one request model and can keep DB-heavy async services entirely off a sync bridge. The strongest reason to choose it would be sustained evidence across several products that native async SQL, WebSockets and FastAPI integrations are their common path. Concurrent SQLAlchemy tasks require separate AsyncSession instances; coordinating related writes still requires a single transaction owner. [FastAPI Users](https://fastapi-users.github.io/fastapi-users/latest/) · [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html) · [Alembic review of generated migrations](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)
4. **Hybrid.** Django/allauth/DRF own accounts, conventional HTTP and admin. The optional extra owns an explicit async HTTP/socket prefix and a small integration contract described below. Keep business rules, schema ownership and consumer test fixtures in ordinary importable packages. No feature may require a second copy of its permission rule to work on the extension. The comparative benefit is access to actual FastAPI-native routers and independently tunable transport code. It has the largest permanent test surface even if initial engineering is fully funded. [FastAPI sub-applications](https://fastapi.tiangolo.com/advanced/sub-applications/)

## A defensible hybrid boundary

### Routing and lifecycle

Run one Uvicorn deployment behind a same-origin TLS proxy. A root ASGI callable owns lifespan and dispatches by protocol and exact path prefix. Django handles HTTP for accounts, admin and conventional APIs. When enabled, FastAPI handles HTTP under `/ext/async/` and WebSockets under `/ext/ws/`. Handle unknown sockets explicitly; never pass a WebSocket or lifespan scope to Django’s HTTP handler. Initialize Django once before importing model-dependent routers. Keep import-time code free of network I/O. Check prefix collisions, trailing slashes, proxy root paths, redirects and docs URLs. Publish separate, versioned schemas or a validated index of them.

Make one component responsible for entering and exiting each enabled resource context once per worker/event loop. Lifespan on a mounted FastAPI sub-app does **not** automatically run under the parent. Start HTTP clients and any async pools after worker creation, publish readiness only after mandatory local initialization, and unwind partially initialized resources on failure. During shutdown stop admitting long connections, cancel upstream work, give active transactions a finite drain interval and close resources in reverse order. Test startup failure, cancellation and repeated worker replacement. [ASGI lifespan specification](https://asgi.readthedocs.io/en/latest/specs/lifespan.html) · [FastAPI lifespan and sub-applications](https://fastapi.tiangolo.com/advanced/events/#sub-applications)

Package the adapter as an optional extra. The core must install and boot without importing FastAPI or creating its clients, routes, migration requirements or pools. An explicitly enabled but invalid extension fails deployment with a diagnostic. An optional upstream outage after startup should mark its feature degraded and return a bounded error while ordinary login and CRUD continue. A runaway synchronous callback, process crash, CPU-heavy codec or OOM can still affect both apps. Per-feature concurrency limits, bounded queues and memory budgets reduce interference; separate processes are the escalation path when those limits cannot protect core traffic.

### Identity is more than reading a cookie

Mounting two apps shares the HTTP origin and potentially the browser cookie. Django’s authentication, CSRF, host validation, session rotation and request middleware apply to the Django branch only. CORS does not authorize a WebSocket handshake. Choose a single browser session authority and a single policy implementation for all four trials. [Django sessions](https://docs.djangoproject.com/en/5.2/topics/http/sessions/) · [Django CSRF](https://docs.djangoproject.com/en/5.2/ref/csrf/) · [Channels WebSocket security](https://channels.readthedocs.io/en/stable/topics/security.html)

| Operation | Proposed hybrid contract |
|---|---|
| Register, log in, recover, log out | Only Django/allauth mutates login state, rotates the session, sets cookies and exposes recovery. Use its browser protocol with CSRF. The FastAPI branch cannot mint login sessions or accept an arbitrary user ID/header as identity. [allauth headless protocol](https://docs.allauth.org/en/latest/headless/openapi-specification/) |
| Authenticate a socket | Put a narrowly configured origin/host validator and Channels’ read-only session/auth middleware around the socket branch, then expose a verified principal to the FastAPI dependency from the ASGI scope. This specific composition is a **candidate to prove** with the selected session engine, auth backends and versions. Require an exact browser Origin allowlist, TLS and valid session before granting access. Reject missing or null Origin in this browser-only profile. Anonymous and partial/MFA-pending sessions receive no private access. |
| Authenticate extension HTTP | For endpoints that need Django cookie semantics, prefer keeping the endpoint in Django/Ninja. If the hybrid must support cookie-authenticated FastAPI HTTP, qualify an adapter that evaluates Django’s actual session/backend/hash and CSRF machinery for the original method, host, origin, headers and cookie. Pin supported body/content types, e.g. JSON with a CSRF header. Reject unsupported configurations. Channels’ session stack alone does not implement Django HTTP CSRF. Block browser writes on that branch until parity is demonstrated, including anonymous unsafe requests. |
| Alternative when direct bridging is too fragile | A CSRF-protected Django POST can issue a short-lived opaque capability restricted to subject, parent session, resource, operation and audience. Store only a digest in PostgreSQL and atomically consume one-time connection tickets. For a browser socket, send the ticket in a bounded first message over TLS with a short authentication deadline and no private output before validation. Keep tickets out of URLs and logs. Expiry, replay, outstanding tickets after logout and revocation all need tests. This introduces an extra round trip and credential lifecycle; choose it only for a specific integration. |
| Enforce row permissions | Resolve the principal, call the same domain policy with actor, resource and action, and scope the query. Derive ownership on the server. List, aggregate, export and document-switch messages all require scope checks. Mutations validate permissions and expected state inside the transaction when changes can race. HTTP serializers and socket message schemas allowlist fields separately. |
| Keep permissions current | Authenticate the handshake and authorize the first resource. Check fresh authoritative state before each sensitive command or subscription change. For ongoing private media/output propose a five-second maximum revocation window from a committed change, bounded by the session expiry. Test **fresh** session/backend state across workers; rereading a cached scope or user is insufficient. Stop output and cancel upstream work if the deadline expires or validation is unavailable. Never hit PostgreSQL on every audio frame. |

Use one policy catalogue for allowed hosts/origins, protected routes, body/frame sizes, trusted proxy hops, admission limits, secure cookies, redaction and audit event names. Enforce common transport limits at ingress/root, framework-specific CSRF at the applicable HTTP branch, and authorization in domain services. Give each request/connection a correlation ID. Log principal references, action, decision and timings without credential, audio or document contents. Apply consistent error categories but retain the framework’s actual HTTP status/WS close behavior in the documented wire contract. Establish expected results from fixtures independently of either adapter.

### PostgreSQL and the sync/async boundary

**Default path.** The app that defines a Django model owns its migration. FastAPI endpoints call the same domain query or transactional command as Django. A supported async ORM query may be awaited. When a command requires multiple reads/writes under a lock, put the entire transaction in one synchronous service and invoke it via a thread-sensitive bridge with appropriate Django connection cleanup. Return materialized values; never pass a lazy queryset, connection or cursor between tasks or threads. Django 5.2 documents the synchronous transaction boundary and recommends disabling persistent connections in async mode. Channels documents connection cleanup for long-lived consumers. [Django async queries and transactions](https://docs.djangoproject.com/en/5.2/topics/async/) · [Channels database access](https://channels.readthedocs.io/en/stable/topics/databases.html)

**Direct async SQL escape hatch.** If profiling shows the bridge dominates a read-heavy path, allow a narrowly scoped psycopg AsyncConnectionPool and reviewed, parameterized SQL against Django-owned tables or versioned views. Start read-only with restricted privileges. Keep the same principal and visibility rules; if they cannot be faithfully applied using a shared authorized query boundary, keep the operation in the Django service. Indexes and views still arrive through Django migrations. A justified async write path must own its entire command and connection transaction, including invariants and idempotency; never write half through Django and the other half via an independent pool. Prohibit schema creation and Alembic on the hybrid branch. Pin query compatibility across rolling upgrades. Release connections before external awaits or streaming. [psycopg connection pools](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)

**Connection budget example.** With two workers and a 16-connection application budget, start Django-only trials at 8 per worker. A hybrid with a measured need for a second pool might use 6 Django + 2 async per worker. At rollout overlap, four workers may use 32; with PostgreSQL max 50 reserve the remainder for release jobs, health checks, operators and PostgreSQL-reserved slots. Recalculate for replicas and surge. Use finite acquisition, query, lock and command deadlines. Track idle-in-transaction time, pool waits, reauthorization reads and connections after disconnects. Pool caps can strand capacity on a quiet branch; compare with a single pool first. [Django PostgreSQL connection management](https://docs.djangoproject.com/en/5.2/ref/databases/)

### Where an async advantage can survive

For a voice relay, the useful work between frames is a bounded read, a bounded enqueue and a write. If session validation happens at connect and on a bounded schedule, and the upstream SDK is truly asynchronous, an async handler can spend most of its lifetime suspended without holding a database connection or dedicated thread. This hypothesis applies to both Channels and FastAPI. For registration the password hash, uniqueness constraint and transaction dominate plausible savings. For CRUD, middleware adaptation and bridge queueing could matter; measure them separately. A synchronous middleware in an otherwise async Django chain can retain a thread per request. Conversely, a FastAPI endpoint doing blocking ORM, audio conversion or synchronous HTTP on the event loop can stall unrelated sockets. [Django async performance](https://docs.djangoproject.com/en/5.2/topics/async/#performance) · [Starlette thread pool](https://starlette.dev/threadpool/)

Define a voice transport contract independent of the web framework: negotiate a supported format, sequence frames, cap sizes and queued milliseconds, run inbound and outbound flows independently, cancel provider generation on interruption, close both peers on disconnect and account for provider minutes. Slow peers require an explicit drop/close policy. Native browser microphone permissions, codec CPU time, WAN delays, provider processing and acoustic echo affect the product independently of ASGI. Use WebSockets to benchmark the proposed relay. Revisit WebRTC or direct provider media if the actual product requires different network/media behavior.

## Matched feasibility and benchmark protocol

**Build the fixtures only after design approval.** Give each candidate the same externally visible operations: register, start/end a browser session, list and edit owned records, reserve stock, aggregate three provider responses, stream events and conduct a duplex voice session. Use the same authorization decision table and fixtures for all candidates. Keep test clients black-box. Allow idiomatic framework implementations. Compare equivalent security, SQL work and response fields; a prototype that omits a permission query, disables CSRF or replaces a password hash with a stub cannot qualify.

**Baseline and attribution.** For option 1 run native Django async HTTP for the streaming scenario and mark plain DRF WebSockets/audio *unsupported*. Run a separately labeled DRF + Channels control to isolate the choice of HTTP framework. For options 2 and 4 run identical Django auth endpoints and domain services. Run the hybrid with the extra disabled, enabled and idle, and carrying traffic. For option 3 match password parameters, storage durability, transaction isolation and indexes. Run hybrid ORM and direct async SQL as separate variants with the same total pool budget. Include a diagnostic public no-DB endpoint and a provider-only relay, then repeat with real auth and policies; only the protected runs count for selection.

**Conditions.** Begin with the blueprint's Linux 4-vCPU/8-GiB app-plus-DB envelope, PostgreSQL 17, two Uvicorn workers, a TLS proxy and sixteen runtime DB connections. Fix CPU/memory limits, database image, disk, indexes, server/driver versions, Python minor, middleware, Argon2 parameters and proxy buffering/timeouts. Use 1,000 synthetic users across disjoint ownership groups and 100,000 seeded records. Put the load generator and deterministic HTTP/audio provider simulators off the measured host. Measure simulator delay separately; record client saturation and offered versus achieved traffic. Use Locust/HTTPX for HTTP, a protocol-aware async socket/audio driver, and a real browser for cookie and CSRF behavior. Record browser, origin, cookie flags and proxy configuration.

At 10, 20, 50 and 100 simultaneous users, warm up for two minutes and measure for five. Use the same seeded sequence of reads, mutations and waits. Also use fixed-rate arrivals at 25, 50 and 100 requests/s to expose queue buildup; measure latency from scheduled arrival and count missed sends. Go to 200+ users to find saturation, then return to 100 and check recovery. Randomize candidate order, reset DB fixtures between runs, run at least five independent repetitions per decision workload. Report per-run p50/p95/p99, throughput, unexpected errors and run-to-run spread. Compare paired differences with uncertainty intervals; increase repetitions if the result is ambiguous. Publish cold startup and idle RSS separately. CPU profiles, loop lag, active threads, bridge wait, hash time, query counts, pool wait, provider time, open FDs and queue depth explain *why* a result differs.

**Mixed load decides the architecture.** While 50 duplex calls run, drive 25 authenticated CRUD requests/s and 5 admitted logins/s for 30 minutes. The protected CRUD/login/voice gates still apply. Target combined app RSS below 1.5 GiB, less than 10% growth between warm and final five-minute medians, bounded queues, zero leaked provider streams and no process kills. Track scheduled revalidation volume: 500 sockets checked every five seconds imply about 100 checks/s before activity-driven checks. Count actual DB queries per check. Batch or jitter refreshes only within the promised security window.

**Recovery and release tests.** Restart one worker with sockets open; expect disconnect/reconnect with a new authorization decision. Interrupt PostgreSQL for 30 seconds; dependent operations return bounded failure, ambiguous writes reconcile by idempotency key, core reads resume within 30 seconds of restoration. Pause the provider simulator and verify healthy login and CRUD. Exercise pool exhaustion, graceful shutdown and stale schemas. Run headless browser smoke, clean install, upgrade from the prior wheel/schema and old/new worker overlap. For the hybrid, verify a missing extra fails only when configured, boot with FastAPI absent, and observe startup/teardown counters exactly once per worker lifecycle. For Channels, demonstrate direct calls across many clients without assuming cross-worker group delivery.

### Decision and release gates

* **Select option 2** if the authenticated feature, mixed-load, recovery and extension tasks meet the targets. A healthy option 1 remains viable where a team depends heavily on DRF; if Ninja fails a security/compatibility gate, retain DRF and trial the separately measured Channels add-on before changing the identity foundation.
* **Promote option 4** after it meets every correctness/security gate and either enables a required vendor feature with materially lower ongoing integration work or delivers a reproducible advantage on a named bottleneck. Proposed threshold: at least 20% more *sustainable* concurrent calls at the same latency and memory budget, or at least 20% lower p95 relay overhead at the same load with no more than 5% degradation of core CRUD p95. Require the improvement across repeat trials with uncertainty small enough to distinguish it, plus two independent consumer examples and a successful dependency upgrade rehearsal. A dispatch-only microbenchmark cannot meet this gate.
* **Reopen option 3** if multiple representative applications need native async DB work or FastAPI integration throughout, and the standalone candidate meets the same browser security, staff, migration, feature-change and recovery requirements. Compare ongoing patch and upgrade work as well as initial assembly time. If all candidates miss the same bottleneck, investigate the shared database, hash budget, provider or proxy before changing frameworks.
* **Publish the evidence** as raw workload configurations, pinned environments, fixture seed, results, policy matrix and a decision record naming the failing or winning workload. Until those exist, the recommendation is a foundation choice for validation, not a capacity guarantee.

Keep it installable independently of simple CRUD apps. Qualify a FastAPI extra or a separate relay deployment only when the decision rule above is satisfied. |

Before a public support promise, resolve the exact Ninja/authenticator behavior on the pinned version, the measured sync-thread and DB costs under ASGI, PostgreSQL-only throttle behavior, and the capacity cost of the revocation deadline. For voice, establish a provider-specific codec, interruption and cancellation contract in a second, consented end-to-end trial; synthetic PCM cannot answer those questions. For a hybrid, also verify the auth adapter against the actual Django backend and any MFA state, and demonstrate safe lifecycle handling at deployment overlap. These results determine which profiles a hackathon team can rely on without rebuilding infrastructure.
